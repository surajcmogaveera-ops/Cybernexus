## Current scope

The Express API owns assignment decisions, plan validation, database writes, and audit records. The deterministic reference policy is `assignment-baseline-v1`. It sorts incidents by effective Phase 11 recommended priority (critical, high, medium, low, then unclassified), earliest persisted SLA deadline, creation time, and incident UUID. For each incident it requires an explicitly known qualification set, exact case-sensitive skill membership, current availability, and a known maximum concurrent assignment count. It selects the least-loaded eligible analyst by workload/capacity ratio, active assignment count, then UUID. Missing qualification data or capacity results in an unassigned escalation. This is a stable greedy baseline, not a global optimum.

The assignment API supports active assignment reads, per-incident assignment history, persisted and auditable baseline recommendations, run retrieval, a bounded what-if simulation, stale/infeasible plan rejection, plan application in a serializable transaction, and authorized manual reassignment. Simulation persists only its run snapshot/result and audit event; it does not mutate Assignment records. Manual changes require `api:write`, a reason, qualifications, availability, and known capacity.

The schema stores analyst skills as tags only; it has no proficiency levels, shifts, location restrictions, estimated effort, or fairness preferences. No such data is inferred. Incident priority/deadline uses the latest persisted Phase 11 calculation, and absent calculation means unclassified/no deadline.

## QpiAI Opt verification

The official [Opt overview](https://opt-api-docs.qpiai.tech/docs/introduction/overview) documents a REST API supporting QUBO, HUBO, and MILP and gives `https://opt-server.qpiai.tech/api` as the base. The [authentication page](https://opt-api-docs.qpiai.tech/docs/introduction/authentication) documents bearer authentication and states the token belongs only in the `Authorization` header. The [error page](https://opt-api-docs.qpiai.tech/docs/introduction/error-codes) documents `{"error":"description"}` and common HTTP status meanings.

The official [PyPI project](https://pypi.org/project/qpiai-opt-api/) describes the legacy `qpiai-opt-api` Python SDK as supporting four fixed combinatorial problems (Maximum Cut, Minimum Vertex Cover, Maximum Independent Set, and Number Partition) plus a general QUBO design engine. Its latest listed release is 1.0.6 from July 2024. The QpiAI-maintained [GitLab SDK project](https://gitlab.qpiai.tech/qpiquantum/optimisation/qpiai-opt-api) says a later SDK update added polling, but its source/tutorial contents could not be read through the public project view in this review. Neither accessible source establishes that the SDK supports arbitrary MILP assignment models. The new REST overview's MILP mention alone does not establish the request schema, supported variable/constraint representation, solver selection, or whether the legacy SDK is compatible with that REST API.

The accessible official material does not provide verifiable concrete request/response schemas for problem creation, solver execution, job status, result retrieval, or quota/credit preflight. There is also no documented guarantee that an authenticated root/read-only request is non-chargeable. Therefore no provider endpoint or payload is guessed, no authenticated request or optimization job is sent, and no live result or baseline-versus-Opt measurement is claimed. `QPIAI_OPT_BASE_URL` and `QPIAI_OPT_API_TOKEN` are server-side configuration names; their local values were validated without disclosure, and the token is never available to the browser. The deterministic baseline remains usable independently of provider configuration.

Before live integration, QpiAI must provide an official current API example or OpenAPI specification that identifies the supported MILP (or QUBO) model schema, problem creation and execution operations, job polling and result retrieval, solver/resource selection, status/objective/result fields, authentication scope, and quota/credit cost for one small test. It must also clarify whether the maintained SDK release tracks the current REST API.

Historical note: the original Phase 12 plan described QpiAI Agent Hive as deferred to its then-numbered Phase 14. The revised Phase 15 records that the alternative workflow remains unselected; no Agent Hive integration is called or configured.
