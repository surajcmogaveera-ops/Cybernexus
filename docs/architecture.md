# CyberNexus architecture

The React/Vite browser client calls the Node/Express API. The Node API owns authentication, authorization, persistence, and audit writes. It calls the private Python/FastAPI service for internal analysis workflows. PostgreSQL is accessed by the API through Prisma. The browser must never call the AI service or external AI/optimization providers directly. `docs/implementation-plan.md` is the canonical 20-phase roadmap; this file is supporting architecture material. Phase numbers in the detailed legacy technical notes below refer to the former 14-phase numbering unless a paragraph says otherwise.

The React dashboard uses local synthetic fixtures and checks Express `/health`; that liveness check does not verify PostgreSQL readiness. The dashboard is not connected to persisted incident or analysis workflows. The private FastAPI service provides deterministic investigation fallback by default and an optional Gemini adapter gated by `AI_PROVIDER=gemini` plus `GEMINI_LIVE_ENABLED=true`. No live Gemini request has been made; do not enable it before owner review of eligibility and data-use terms. Express validates the response contract and incident-scoped evidence before persistence; claims remain unverified. Deterministic risk/SLA and assignment policies remain application-owned. QpiAI Opt has no verified live integration, and the alternative agent workflow provider is unselected. See the canonical 20-phase plan for current boundaries.

## API and JSON contracts

The TypeScript contracts in `packages/shared` define alert input and records, incidents, analysts, assignments, health responses, and API errors. JSON fields use camelCase, identifiers use UUID strings, and timestamps use ISO 8601 UTC strings ending in `Z`. Provider-specific alert fields stay inside the untrusted `payload` object. The Node API validates request bodies with these schemas and returns errors as `{ "error": { "code": "...", "message": "...", "details": [{ "path": ["field"], "message": "..." }] } }`; error responses never include stack traces.

Python does not import TypeScript. FastAPI and Pydantic exchange ordinary JSON using the same field names and UTC timestamp convention. The web client validates the Node health response against the shared health contract. The Python health endpoint uses the same `status` and `service` field names, with its exact JSON shape covered by the Python endpoint test. The Vite development server proxies `/api/*` to the Node API and removes the `/api` prefix.

### Express API access controls

Express exposes a versioned `/api/v1/session` identity endpoint and `/api/v1/alerts` ingestion/list routes. Versioned API routes are rate-limited before authentication and require a configured bearer credential. Configure `CYBERNEXUS_API_TOKENS_JSON` as a JSON array of `{ "token", "subject", "scopes" }` records in an ignored local environment file or deployment secret store. Tokens must be high-entropy values of at least 32 characters; supported scopes are `api:read`, `api:write`, and `audit:write`. Alert list reads require `api:read`; ingest and batch upload require `api:write`. Missing or malformed token configuration fails closed with a safe 503 response; absent or invalid credentials receive 401, and insufficient scopes receive 403. `/health` remains a public process-liveness endpoint. Gateway access errors use a separate shared TypeScript schema so the established FastAPI service error contract remains unchanged.

Each HTTP response receives a server-generated `X-Request-ID`; inbound request IDs are not trusted or propagated. The in-memory fixed-window limiter defaults to 120 requests per minute per Express client IP, with bounded tracking state and `Retry-After` guidance. Express proxy trust remains disabled, so deployments behind a proxy must set a reviewed proxy policy before relying on client-IP rate limits. The in-memory limiter is process-local and does not replace a distributed gateway limiter for multi-instance production deployment. The token configuration is a Phase 6 access-control foundation, not a user directory or production identity lifecycle: token rotation, revocation, expiry, and operator provisioning remain deployment responsibilities.

`apps/api/src/audit/write-audit-event.ts` validates and persists bounded audit metadata using a caller-supplied Prisma transaction client. Future business writes must call it within the same transaction as the action being audited. The current Phase 6 routes do not perform domain writes, and audit events are not made tamper-proof by this helper.

### Versioned service contracts

The first shared wire-contract revision is `v1`. New public APIs should use `/api/v1`; internal analysis messages carry `contractVersion: "v1"`. Additive optional fields may be introduced compatibly. Changes to required fields, meaning, accepted values, or bounds normally require a new major contract version and an explicit migration/compatibility window; unknown versions are rejected. The approved Gemini adapter adds `gemini` to the existing `analysisMethod` enum without changing the response shape, and all in-repository Python and TypeScript consumers are updated together. Strict external v1 consumers must update before Gemini is enabled. Do not treat this coordinated extension as blanket permission to change other accepted values without versioning. Do not add a version field to unrelated domain records.

UTC timestamp strings must be valid ISO 8601 date-times ending in `Z`; local times and numeric offsets are rejected. Identifiers follow the existing Zod UUID validator, including its all-zero UUID allowance. Models reject unknown fields. API error codes are `VALIDATION_ERROR`, `MALFORMED_JSON`, `NOT_FOUND`, `UNSUPPORTED_CONTRACT_VERSION`, and `INTERNAL_SERVER_ERROR`; messages and structured path/message details are bounded. Internal exception text and stack traces are never part of the wire format.

List contracts use offset pagination: `page` is one-based (default 1), `pageSize` defaults to 25 and is bounded from 1 to 100. Responses include `items`, requested page metadata, `hasNext`, and optional `totalItems`, defined as the matching count observed for that request (not a cross-request snapshot guarantee). Analysis requests allow at most 100 alert IDs and at most 100 evidence references (up to 200 entries combined), with 4,000 context characters; results allow at most 20 findings and each finding is explicitly `unverified`. Evidence references identify data but do not validate claims. Analysis is advisory; the deterministic fallback is default and Gemini is optional behind an explicit server-side live-call gate.

`packages/shared/fixtures/contracts-v1.json` is the common JSON fixture consumed by TypeScript and Python tests. Run `pnpm --filter @cybernexus/shared test` and `python -m pytest services/ai/tests -q` with the project virtual environment active. Python uses Pydantic equivalents; it must not import TypeScript. Pydantic wire serialization omits absent optional fields; explicit `null` is rejected for those fields. Fixture tests cover matching examples and key rejection cases, while later phases must still validate evidence and enforce application policy.

## PostgreSQL and Prisma persistence

The API is the only service permitted to write authoritative application data. PostgreSQL rows use application-generated UUID primary keys and UTC `TIMESTAMPTZ(6)` values; `@updatedAt` fields are set by Prisma. PostgreSQL enums match the current severity, incident, availability, assignment, evidence-kind, analysis-run, verification, and contract-version values. JSONB is limited to raw alert payloads, source metadata, normalized attributes, and structured audit metadata.

`SecurityAlert` keeps the original provider payload in JSONB, separately from optional normalized attributes and provenance metadata. `externalId` is optional. A unique `(source, externalId)` index prevents duplicate use of a reliable source event ID while PostgreSQL permits multiple `NULL` IDs. A unique `(source, idempotencyKey)` index supports exact client retries where a source ID is absent; without either identifier, separate submissions are retained. Reusing an identity for different normalized content returns a conflict and never overwrites the stored row. A migration preflight must identify any existing duplicate non-null source IDs before the unique index is applied; the migration does not merge or delete rows. `IncidentAlert` is an explicit many-to-many join; an alert can remain ungrouped or be associated with multiple incidents. The `Incident.needsHumanReview` nullable Boolean maps to the optional TypeScript contract property: database `true` maps to contract `true`, database `false` maps to contract `false`, and database `NULL` maps to an omitted property (never explicit JSON `null`). Phase 9 incident creation sets review to true, and its incident mapper omits database `NULL`. Phase 10 analysis runs link to known alert rows; polymorphic evidence references store kind, UUID, and field paths. Express validates that references point to supplied, incident-scoped records and allowed fields, but this does not prove a cited field semantically supports a claim. Findings persist as `unverified`. Analysis confidence is a fallback coverage fraction over distinct cited source records, not a probability or risk score. Incident risk scores remain deferred to Phase 11. Analyst skills are separate searchable rows; assignments retain separate historical records. Phase 12 adds explicit incident skill requirements with a known/unknown flag, nullable maximum concurrent assignments, and persisted optimization-run input/result snapshots. The baseline escalates when requirements or capacity are unknown. Audit events have a polymorphic target and no target foreign key, so they can remain as history; append-only behavior is an application convention, not a tamper-proof guarantee.

The shared Incident contract requires at least one alert ID. Phase 9 creates incidents only from candidate relationship components of at least two alerts and writes the incident and its `IncidentAlert` rows inside the same transaction as entity links, candidate relationships, and audit events. Existing ungrouped alerts remain valid. The relational schema does not enforce a nonempty child collection; direct database writers can bypass this application-layer invariant, so all authoritative writes must remain inside Express workflows.

Foreign keys use `RESTRICT` on delete and update. No cascade can erase alerts, assignments, analysis records, or their history. There is no retention or purge policy yet. The initial migration contains explicit PostgreSQL checks for analysis `maxFindings` (1–20) and finding confidence (0–1); Prisma 6 does not represent these checks in the schema, so retain and review them in future migration SQL. Other write bounds remain application-validation responsibilities.

Prisma CLI and client are both 6.19.3 in the installed workspace. `apps/api/prisma.config.ts` supplies the migration path, seed command, and `DATABASE_URL`; `.env.example` contains only a local placeholder. With a local PostgreSQL database configured, use `pnpm --filter @cybernexus/api prisma:generate`, then `pnpm --filter @cybernexus/api prisma:migrate:deploy`. Use `pnpm --filter @cybernexus/api prisma:migrate` only against a local development database to create/apply migrations. Prisma 6 may run the configured seed during `migrate dev`; it is synthetic and idempotent. Run it explicitly with `pnpm --filter @cybernexus/api prisma:seed` when using deploy migrations.

The deterministic seed uses fixed identifiers and synthetic-only records. The reusable Prisma client is in `apps/api/src/db/prisma.ts`; the HTTP server disconnects it during SIGINT/SIGTERM shutdown. Importing it does not connect, and `/health` remains a process liveness response that does not claim database readiness.

Database-independent checks are `pnpm typecheck`, `pnpm test`, and `pnpm build`. PostgreSQL integration tests live in `apps/api/src/db/database.integration.test.ts` and are skipped unless `CYBERNEXUS_TEST_DATABASE_URL` points to a local database named exactly `cybernexus_test`. Prepare that disposable database with `DATABASE_URL` set to the same URL and run `pnpm --filter @cybernexus/api prisma:migrate:deploy`, then run `pnpm --filter @cybernexus/api test -- src/db/database.integration.test.ts`. Tests use random row IDs and clean up only their own rows. In the latest Phase 5 audit, local PostgreSQL databases `cybernexus_dev` and `cybernexus_test` were present; Prisma reported the initial migration applied and up to date in `cybernexus_dev`, and read-only introspection confirmed `Incident.needsHumanReview` is nullable with no default. The test URL was not configured, so integration tests were skipped. This foundation does not provide production retention enforcement, backup/recovery, authorization, or tamper-proof auditing.
